Foundations

The vocabulary every interview opens with. Get these crisp and the rest of the conversation flows.

FND-01 · the umbrella terms

AI vs. ML vs. Deep Learning vs. Gen AI

Basic
Theory

These four words are nested circles, not synonyms. Artificial Intelligence (AI) is the broadest goal: any technique that makes a machine behave in a way we'd call "intelligent" — including old-school rule-based systems with no learning at all.

Machine Learning (ML) is a subset of AI where the system learns patterns from data instead of following hand-written rules. Deep Learning (DL) is a subset of ML that uses many-layered neural networks, which is what made modern image and language systems work. Generative AI is a use-case of deep learning: models that produce new content (text, images, audio, code) rather than just classifying or predicting a number.

  • AI ⊃ ML ⊃ Deep Learning ⊃ (large) Generative models / LLMs.
  • A spam filter using if-rules is AI but not ML. A spam filter that learns from examples is ML.

Interview Q&A
Is every AI system a machine learning system?

No. ML is a subset of AI. A purely rule-based expert system — like a thermostat or a hand-coded chess engine — is AI but uses no learning. ML specifically means the behaviour is derived from data, not authored by a human as explicit rules.

Why did deep learning take off only in the 2010s?

The algorithms (neural nets, backprop) existed for decades. What changed were three enablers: large labelled datasets (e.g. ImageNet), GPU compute that made training feasible, and architectural/optimization advances (ReLU, better initialization, later the Transformer). When all three lined up, deep nets started beating hand-engineered approaches.

Where do LLMs sit in this hierarchy?

An LLM is a deep learning model (specifically a Transformer) used for generative AI over text. So it sits at the innermost circle: AI → ML → Deep Learning → Generative → LLM.

FND-02 · the core object

What is a "model"?

Basic
Theory

A model is a mathematical function that maps inputs to outputs, whose behaviour is determined by a large set of numbers called parameters (or weights). You can think of it as output = f(input, parameters).

Two things define a model: its architecture (the shape of the function — how many layers, how they connect, e.g. a Transformer) and its learned parameters (the specific numbers found during training). The architecture is the empty recipe; the parameters are what fills it after the model has "eaten" data. A saved set of parameters at a point in time is a checkpoint.

  • "GPT-style 7B model" = a Transformer architecture with 7 billion tuned parameters.
  • Same architecture + different training data = a different model.

Interview Q&A
What's the difference between architecture and parameters?

The architecture is the fixed structure you design before training — the number and type of layers and how data flows through them. The parameters are the adjustable numbers inside that structure, set automatically during training. Two models can share an architecture but have completely different parameters because they saw different data.

Does a bigger model (more parameters) always mean a better model?

Not automatically. Scale tends to help, but performance depends on data quality and quantity, training compute, and how well the model is aligned/fine-tuned. A smaller model trained on better data with better technique can beat a larger one — and it's cheaper to run.

What does "loading a model" actually mean?

It means reading the saved parameter values (the checkpoint) into memory and reconstructing the architecture so you can run inputs through them. The "model file" you download is essentially a big array of numbers plus a description of the architecture.

FND-03 · how text becomes numbers

Tokens & Tokenization

Basic
Theory

Models don't read letters or words — they read tokens, which are chunks of text mapped to integer IDs. A token is usually a subword: common words may be one token, while rare or long words split into several. Roughly, 1 token ≈ 4 characters ≈ ¾ of an English word.

The tokenizer is the component that splits text into these chunks (commonly with an algorithm like Byte-Pair Encoding). The full set of possible tokens is the model's vocabulary. Tokens matter for three practical reasons: they define the context window limit, they drive API pricing (you pay per token in and out), and they affect latency (longer outputs take longer because tokens are generated one at a time).

  • "cat" → 1 token. "antidisestablishmentarianism" → several tokens.
  • Whitespace and punctuation count too; non-English text often uses more tokens per word.

Interview Q&A
Why not just feed the model raw words or characters?

Words give a huge, open-ended vocabulary (every typo or new word is unknown). Characters make sequences very long and slow. Subword tokens are the sweet spot: a manageable vocabulary that can still represent any word by composing pieces, handling rare words and typos gracefully.

If a model has a 128k context window, what does that mean?

It can attend to up to 128,000 tokens at once — that's the combined budget for your prompt plus the generated output. Exceed it and earlier tokens must be dropped or summarized. It's a token count, not a character or word count.

You're billed $X per 1M tokens — how do input and output differ?

Providers usually charge separately for input (prompt) tokens and output (completion) tokens, and output is typically more expensive because it's generated step by step. Total cost ≈ (input tokens × input rate) + (output tokens × output rate).

FND-04 · the one people confuse

Model vs. Platform vs. Agent

Basic
Theory

These three sit at different layers of the stack, which is exactly why they get muddled.

A model is the raw brain — the trained function that turns an input into an output. On its own it does nothing until something feeds it text. A platform is the surrounding product and infrastructure that delivers the model: the API, the chat interface, authentication, rate limits, billing, safety filters, storage. The platform is how you actually reach the model.

An agent is a system built on top of a model that can take actions in a loop to reach a goal. Instead of answering once, an agent can decide to call tools (search, run code, hit an API), observe the result, and decide its next step — repeating until the task is done. The model is the agent's reasoning engine; the agent adds memory, tools, and a control loop.

  • Model = the engine. Platform = the car and the dealership. Agent = a self-driving system that uses the engine to get somewhere.
  • A plain chatbot maps one input to one output. An agent plans, acts, observes, and iterates.
Diagram

Interview Q&A
What's the single clearest difference between a model and an agent?

Autonomy and looping. A model produces one output for one input and stops. An agent wraps the model in a control loop: it can decide to take an action (use a tool, call an API), observe the outcome, and choose its next step toward a goal — running multiple model calls without a human in between.

Is ChatGPT a model, a platform, or an agent?

The product is a platform (UI, accounts, history, safety) that serves an underlying model (e.g. a GPT model). When it browses the web or runs code on its own to complete a multi-step task, it's behaving as an agent. The terms describe layers, so one product can involve all three.

Why is "agent" considered harder to build reliably than a chatbot?

Because errors compound across steps. A single wrong answer is one mistake; in an agent, a wrong decision early can send the whole loop off course. Agents also need tool integration, memory, guardrails, and stopping conditions — plus the model has to reliably decide when to act and when it's finished.

FND-05 · the two phases

Training vs. Inference

Basic
Theory

A model's life has two phases. Training is the learning phase: the model sees data, makes predictions, measures how wrong it is (the loss), and adjusts its parameters to be less wrong next time — repeated billions of times. This is expensive, slow, and done once (or occasionally).

Inference is the using phase: the parameters are now frozen, and you simply run new inputs forward through the model to get outputs. Every time you send a prompt and get an answer, that's inference. Training writes the weights; inference reads them.

  • Training = adjust parameters (uses backpropagation + gradient descent). Costly, occasional.
  • Inference = forward pass only, weights frozen. Cheaper per run, but you do it constantly.
Diagram

Interview Q&A
During inference, do the model's weights change?

No. At inference the weights are frozen; the model just runs inputs forward. Any apparent "learning within a chat" comes from the context window (the conversation is fed back in as input), not from updating parameters.

If training is so expensive, why is inference often the bigger cost over time?

Because you train once but infer endlessly. A popular model may serve billions of requests, so the cumulative inference compute — and the engineering to serve it fast and cheap — dwarfs the one-time training run.

What is the "forward pass" vs the "backward pass"?

The forward pass runs input through the network to produce an output (this is all inference needs). The backward pass (backpropagation) happens only in training: it computes the gradient of the loss with respect to each weight so the optimizer can update them.

FND-06 · how models learn

Supervised, Unsupervised & Reinforcement Learning

Basic
Theory

The three classic learning paradigms differ by what signal the model learns from.

Supervised learning uses labelled examples — each input comes with the correct answer (spam/not-spam, price, category). The model learns to map inputs to those known outputs. Unsupervised learning has no labels; the model finds structure on its own — grouping similar items (clustering) or compressing data. Reinforcement learning (RL) learns by acting in an environment and receiving rewards or penalties, optimizing for long-term reward rather than copying labels.

Modern LLMs add self-supervised learning: the data labels itself. "Predict the next token" turns ordinary text into billions of free training examples — no human labelling needed.

Interview Q&A
How are LLMs trained if labelling trillions of words is impossible?

Through self-supervised learning. The task is "predict the next token," so any text is automatically its own label — the next word is the answer. This unlocks training on internet-scale data without manual annotation; human labelling comes later, in smaller fine-tuning/RLHF stages.

Give a clean example of supervised vs unsupervised on the same data.

Take customer records. Supervised: predict "will churn / won't churn" using past examples labelled with the outcome. Unsupervised: with no labels, cluster customers into natural segments and let a human interpret the groups afterward.

Why is reinforcement learning harder than supervised learning?

The feedback is sparse and delayed — a reward may come many steps after the action that caused it (the credit-assignment problem). There's also an exploration vs exploitation tradeoff: the agent must try new actions to learn while still using what works. Supervised learning, by contrast, gets the right answer immediately for every example.

FND-07 · the central failure mode

Overfitting, Underfitting & Generalization

Basic
Theory

The whole point of ML is generalization: doing well on data the model has never seen, not just the training set. Two failure modes block that.

Overfitting is when a model memorizes the training data — including its noise — so it scores high on training but poorly on new data. Underfitting is the opposite: the model is too simple to capture the real pattern, so it does poorly on both training and new data. The sweet spot lies between, and this is the bias–variance tradeoff: high bias = underfit (too rigid), high variance = overfit (too sensitive to the specific data).

  • Overfit signal: training accuracy ≫ validation accuracy.
  • Fixes: more data, regularization (e.g. dropout, weight decay), simpler model, early stopping.

Interview Q&A
How do you detect overfitting?

Hold out data the model never trains on. If training performance keeps improving while validation performance stalls or worsens, the model is overfitting. The growing gap between train and validation curves is the classic tell.

Why do we split data into train, validation, and test sets?

Train fits the parameters. Validation tunes choices like hyperparameters and tells you when to stop. Test is touched only once at the end to estimate real-world performance. Keeping test separate prevents you from unconsciously overfitting to it through repeated tweaking.

Name a few ways to reduce overfitting.

Get more (or more varied) data, apply regularization (weight decay, dropout), use a simpler model, add data augmentation, and use early stopping to halt before the model starts memorizing. Cross-validation also gives a more honest performance estimate.

FND-08 · what the model doesn't know

Knowledge Cutoff

Basic
Theory

A model's knowledge cutoff is the date after which it has no built-in information. Its parameters were frozen during training on data collected up to that point, so anything that happened later — news, releases, prices, election results — simply isn't in the weights. Ask about it and the model will either say it doesn't know or, worse, hallucinate a plausible-sounding guess.

This is a direct consequence of training and inference being separate phases: knowledge is baked in at training time and doesn't update on its own. To give a model fresh information you don't retrain it — you supply the facts at inference time via the context window, using RAG or live tool/web access. Cutoff is about parametric knowledge; retrieval adds external knowledge.

  • Cutoff ≠ today. There's also a lag between the cutoff and a model's public release.
  • Fix stale answers with retrieval or search tools, not by hoping the model "knows."
Cheat sheet
quick recall
CutoffLast date in training data; no built-in knowledge after it.

SymptomWrong/"I don't know" on recent events; confident hallucination.
FixFeed facts at inference: RAG or live web/tool access.
NoteParametric knowledge (cutoff) vs external knowledge (retrieval).
Interview Q&A
A user asks your LLM app about something that happened yesterday. How do you handle it?

Don't rely on parametric memory — it's past the cutoff. Retrieve current information (a web-search tool or a freshly updated knowledge base) and pass it into the prompt so the model answers from real, recent context. Ideally also have the model cite the source and acknowledge uncertainty when retrieval finds nothing.

Does a bigger context window remove the need to worry about cutoff?

No — they're different things. The cutoff limits what the model learned during training; the context window is how much you can feed it at runtime. A huge window helps you inject fresh data, but the fresh data still has to come from somewhere (retrieval/tools). The window is the delivery channel, not the knowledge.

Core Concepts

How modern language models actually work, and the levers you pull when you use one.

CORE-01 · the building block

Neural Networks

Intermediate
Theory

A neural network is layers of simple units ("neurons") connected by weighted links. Each neuron multiplies its inputs by weights, adds a bias, and passes the result through a non-linear activation function (like ReLU). Stack enough of these layers and the network can approximate extremely complex input→output relationships.

The non-linearity is the secret. Without an activation function, stacking layers would collapse into a single linear function no matter how deep. Non-linear activations let each layer build richer features on top of the last — edges → shapes → objects, or letters → words → meaning.

  • Input layer → hidden layers → output layer.
  • "Deep" simply means many hidden layers.
Diagram

Interview Q&A
Why do neural networks need non-linear activation functions?

Because a composition of linear functions is still just one linear function. Without non-linearity, a 50-layer network would have no more expressive power than a single layer. Activations like ReLU introduce the non-linearity that lets deeper layers represent progressively more abstract features.

What is the vanishing gradient problem?

In very deep networks, gradients can shrink toward zero as they propagate backward, so early layers barely update and learning stalls. Mitigations include ReLU activations, careful weight initialization, residual/skip connections, and normalization layers — all of which help gradients flow.

CORE-02 · meaning as geometry

Embeddings

Intermediate
Theory

An embedding is a list of numbers (a vector) that represents a piece of data — a word, sentence, image, or document — in a way that captures its meaning. The key property: similar things land close together in this high-dimensional space, while unrelated things are far apart.

This turns "meaning" into geometry. You can measure how related two texts are by the cosine similarity (angle) between their vectors. Embeddings are the backbone of semantic search, recommendations, clustering, and Retrieval-Augmented Generation — anywhere you need "find me things like this" rather than exact keyword matches.

  • "king" − "man" + "woman" ≈ "queen" — relationships become vector arithmetic.
  • Search by meaning: "car" matches "automobile" even with no shared letters.

Interview Q&A
How is semantic search different from keyword search?

Keyword search matches exact strings — "automobile" won't find "car." Semantic search compares embeddings, so it matches on meaning: "car," "automobile," and "vehicle" all sit near each other in vector space and retrieve one another regardless of shared characters.

Why cosine similarity rather than plain distance?

Cosine similarity measures the angle between vectors, ignoring their magnitude. For text embeddings, direction tends to encode meaning while magnitude can vary with length or frequency, so comparing direction gives a cleaner relatedness signal. (It's also bounded between −1 and 1, which is convenient.)

CORE-03 · the architecture behind everything

Transformers & Attention

Intermediate
Theory

The Transformer (2017, "Attention Is All You Need") is the architecture under almost every modern LLM. Its core mechanism is self-attention: for each token, the model looks at every other token in the sequence and decides how much each one should influence its representation. This lets it capture long-range relationships — linking a pronoun to a noun many words earlier, for example.

Attention works through queries, keys, and values: each token emits a query ("what am I looking for?") and a key ("what do I offer?"); their match scores decide how much of each token's value gets mixed in. Because attention compares all tokens at once, Transformers process sequences in parallel (unlike older RNNs that went word-by-word), which is why they scale so well on GPUs. Positional encodings are added so the model still knows word order.

Interview Q&A
Why did Transformers replace RNNs/LSTMs for language?

RNNs process tokens sequentially, which is slow and makes long-range dependencies hard to learn (information fades over distance). Transformers use attention to see the whole sequence at once, so they parallelize on GPUs and connect distant tokens directly. That combination unlocked training on far larger data and models.

In one line, what does self-attention do?

For every token, it computes a weighted blend of all other tokens, where the weights reflect how relevant each token is — letting the model build context-aware representations.

What's the main computational cost of attention?

Standard self-attention is quadratic in sequence length (every token attends to every other), so doubling the context roughly quadruples the attention compute and memory. This is why long-context models need optimizations like FlashAttention or sparse/linear attention variants.

CORE-04 · what an LLM really does

Large Language Models (LLMs)

Intermediate
Theory

An LLM is a large Transformer trained to do one deceptively simple thing: predict the next token given the tokens so far. It outputs a probability distribution over the whole vocabulary, picks a token, appends it, and repeats — this is called autoregressive generation. Everything an LLM appears to "know" or "reason" emerges from doing this at massive scale.

Training has stages: pre-training on huge unlabelled text (learning language and world patterns via next-token prediction), then fine-tuning / instruction-tuning and alignment (RLHF) to make it follow instructions helpfully and safely. The raw pre-trained model just continues text; the aligned model behaves like an assistant.

  • It doesn't "look up" answers — it generates the most probable continuation.
  • That's also why it can hallucinate: plausible-sounding text isn't always true.

Interview Q&A
Does an LLM "understand" language or just predict text?

Mechanically it predicts the next token. But to predict well across vast contexts it builds internal representations that capture syntax, facts, and relationships — which behaves like a useful, if imperfect, form of understanding. The honest interview answer: it's prediction that yields emergent competence, while lacking grounding, true beliefs, or guaranteed factual accuracy.

Why does an LLM hallucinate?

It's optimized to produce probable, fluent continuations, not to verify truth. When it lacks the knowledge, it still generates the most plausible-sounding text, which can be confidently wrong. Mitigations include retrieval (RAG) to ground answers, and prompting it to express uncertainty or cite sources.

What's the difference between a base model and an instruct model?

A base (pre-trained) model just continues text statistically — ask it a question and it might continue with more questions. An instruct/chat model has been fine-tuned and aligned (often with RLHF) to follow instructions and respond as a helpful assistant.

CORE-05 · the model's working memory

Context Window

Intermediate
Theory

The context window is the maximum number of tokens a model can consider at once — its short-term working memory. Everything the model "remembers" in a conversation lives here: the system prompt, the chat history, your current question, and the space reserved for its answer all share this single budget.

Crucially, the model has no memory between separate calls. The illusion of memory in a chat comes from re-sending the conversation each turn. When the conversation exceeds the window, older content must be dropped, summarized, or retrieved on demand. Bigger windows help, but very long contexts can dilute attention (the "lost in the middle" effect) and cost more.

Interview Q&A
How does a chatbot "remember" earlier messages if models are stateless?

It doesn't, internally. The application resends the prior conversation as part of the prompt on every turn. The model re-reads that history within its context window each time, which produces the feeling of memory. Drop the history and the "memory" vanishes.

A 1M-token context window sounds like it solves memory. What's the catch?

Cost and attention quality. Processing huge contexts is slower and more expensive, and models can struggle to use information buried in the middle of very long inputs. For persistent or huge knowledge, retrieval (RAG) is often better than stuffing everything into context.

CORE-06 · steering without retraining

Prompt Engineering

Intermediate
Theory

Prompt engineering is shaping a model's output purely through its input — no retraining required. Because an LLM continues from whatever you give it, the wording, structure, examples, and constraints you provide strongly steer the result.

Core techniques: zero-shot (just ask), few-shot (include a handful of input→output examples so the model infers the pattern), and chain-of-thought (ask it to reason step by step, which improves multi-step problems). A system prompt sets persistent role and rules. Good prompts are specific about role, task, format, and constraints, and often give positive examples of the desired output.

Cheat sheet

Interview Q&A
When would you use few-shot over zero-shot?

When the task has a specific format or style that's hard to describe but easy to demonstrate, or when zero-shot results are inconsistent. A few well-chosen examples anchor the output format and reduce ambiguity — at the cost of extra tokens.

Why does chain-of-thought prompting improve accuracy?

It lets the model spend more tokens "working through" intermediate steps instead of jumping to an answer. Since each token is conditioned on the ones before it, externalizing the reasoning gives the model scaffolding to reach correct multi-step conclusions, especially for math and logic.

When is prompt engineering not enough, and you need fine-tuning?

When you need consistent specialized behaviour, a domain style, or to bake in knowledge/format at scale that's too large or repetitive to fit in every prompt. Prompting is fast and flexible; fine-tuning is worth it when you have many examples and need reliability or lower per-call token cost.

CORE-07 · the output dials

Temperature, Top-k & Top-p

Intermediate
Theory

At each step an LLM produces a probability distribution over possible next tokens. Sampling parameters control how that distribution is turned into an actual choice — trading off determinism against creativity.

Temperature scales the distribution: low (→0) makes it sharp and near-deterministic (always pick the likeliest token); high (→1+) flattens it, making rarer tokens more likely and output more varied. Top-k restricts the choice to the k most likely tokens. Top-p (nucleus) keeps the smallest set of tokens whose probabilities sum to p, adapting the cutoff to the situation. These filters and temperature are usually combined.

Interview Q&A
You're building a code generator — what temperature and why?

Low temperature (near 0). Code needs to be precise and reproducible; you want the model to pick the most probable, correct tokens rather than explore creative-but-broken variations. High temperature is for tasks where variety is the goal, like ideation or storytelling.

What's the difference between top-k and top-p?

Top-k uses a fixed count — always the k likeliest tokens, regardless of how confident the model is. Top-p (nucleus) uses a fixed probability mass, so the candidate set shrinks when the model is confident and grows when it's uncertain. Top-p adapts to the distribution; top-k doesn't.

CORE-08 · specializing a model

Pre-training vs. Fine-tuning

Intermediate
Theory

Pre-training builds general capability: a model learns language and broad world knowledge from enormous unlabelled data via next-token prediction. It's hugely expensive and done rarely. Fine-tuning takes that pre-trained model and continues training it on a smaller, focused dataset to specialize it — a domain (legal, medical), a task (classification), or a style/behaviour.

This is transfer learning: reuse the general knowledge, adapt the edges. Instruction-tuning is a fine-tuning step that teaches a model to follow instructions. Fine-tuning changes the weights, unlike prompting or RAG which only change the input.

Cheat sheet
quick recall

Fine-tuningSpecialize on a smaller focused dataset. Changes weights.
Transfer learningReuse general model, adapt to a new task cheaply.
vs Prompting/RAGThose change input only; fine-tuning changes the model.
Use it forConsistent style/format, domain behaviour, lower per-call cost.
Interview Q&A
Fine-tuning vs RAG — when do you pick which?

Use RAG when the need is up-to-date or large external knowledge — it injects facts at query time without retraining and is easy to update. Use fine-tuning when you need to change behaviour, style, or format consistently, or specialize on a task. They're complementary: fine-tune for how to respond, RAG for what facts to use. Often you do both.

What is catastrophic forgetting?

When fine-tuning on new data causes a model to lose previously learned capabilities, because the weights shift too far toward the new task. Mitigations include lower learning rates, mixing in original-style data, and parameter-efficient methods like LoRA that touch only a small part of the model.

CORE-09 · giving the model facts

Retrieval-Augmented Generation (RAG)

Intermediate
Theory

RAG lets a model answer using knowledge it wasn't trained on, without retraining. The flow: take the user's question, retrieve the most relevant documents from a knowledge base (usually via embedding similarity in a vector database), and inject those passages into the prompt so the model generates a grounded answer.

It directly attacks two LLM weaknesses: stale knowledge (the model's training has a cutoff) and hallucination (grounding answers in real retrieved text, often with citations). A typical pipeline: chunk documents → embed them → store in a vector DB → at query time, embed the question, find nearest chunks, and pass them to the model.

Diagram
Cheat sheet
quick recall
RAGRetrieve relevant docs → put in prompt → model answers from them.
PipelineChunk → embed → store → retrieve nearest → generate.
SolvesStale/limited knowledge & hallucination; enables citations.
No retrainingUpdate the knowledge base, not the weights.
Quality hinges onRetrieval. Bad chunks in → bad answer out.
Interview Q&A
Walk me through a basic RAG pipeline.

Indexing (offline): split documents into chunks, create an embedding for each, store them in a vector database. Query time: embed the user's question, retrieve the top-k most similar chunks, insert them into the prompt as context, and have the LLM generate an answer grounded in those chunks — ideally with citations back to the sources.

RAG gives a wrong answer. Where do you look first?

Usually retrieval, not generation. Check whether the right chunks were even retrieved: bad chunking, weak embeddings, a too-small top-k, or no relevant document in the store all starve the model of correct context. If the right context was retrieved but the answer is still wrong, then look at the prompt and the model.

Why chunk documents instead of embedding whole files?

Because retrieval needs to return focused, relevant passages that fit in the context window. A whole document's embedding blurs many topics into one vector, hurting match precision and wasting context on irrelevant text. Sensible chunk sizes (often with overlap) keep each vector semantically tight.

CORE-10 · the trust problem

Hallucination

Intermediate
Theory

Hallucination is when a model produces confident, fluent output that is factually wrong or fabricated — invented citations, made-up APIs, false dates. It's not a bug so much as a side-effect of how LLMs work: they're trained to generate plausible text, and plausibility doesn't guarantee truth.

It worsens when the model is asked about things outside its training, niche facts, or specifics it never reliably learned. Key mitigations: grounding answers with retrieval (RAG), prompting for citations and uncertainty, letting the model say "I don't know," using tools to verify, and human review for high-stakes use.

Cheat sheet
quick recall
WhatConfident output that's false or fabricated.
WhyModels optimize for plausible text, not verified truth.
Worse whenNiche facts, recent events, exact figures, things untrained.
Reduce withRAG grounding · citations · "I don't know" · tools · review.
Can't fullyeliminate — design systems assuming it can occur.
Interview Q&A
Can hallucination be completely eliminated?

Not entirely with current LLMs — it's intrinsic to generating probable text. You can substantially reduce it (grounding with RAG, verification tools, lower temperature, asking for citations) and contain it (human review, refusing when unsure), but a responsible system is designed assuming hallucinations can happen, especially in high-stakes domains.

How does RAG reduce hallucination but not remove it?

RAG gives the model real retrieved text to ground its answer, so it relies less on shaky parametric memory. But the model can still misread, over-generalize, or ignore the retrieved context, and if retrieval returns nothing relevant, it may fall back to guessing. Grounding lowers the rate; it doesn't guarantee truth.

CORE-11 · how good is it, really

Evaluation Metrics

Intermediate
Theory

You can't improve what you can't measure. For classification, the staples are accuracy (overall correct), precision (of predicted positives, how many were right), recall (of actual positives, how many were caught), and F1 (their harmonic mean). Which one matters depends on the cost of false positives vs false negatives.

For generative models, evaluation is harder because there's no single right answer. Approaches include perplexity (how well the model predicts held-out text), overlap metrics like BLEU/ROUGE (for translation/summarization), benchmarks (standardized test suites), human evaluation, and increasingly LLM-as-judge (using a capable model to score outputs).

Cheat sheet
quick recall
Accuracy% correct. Misleading on imbalanced data.
PrecisionOf flagged positives, how many were truly positive.
RecallOf all true positives, how many you caught.
F1Harmonic mean of precision & recall. Balances both.
GenerativePerplexity · BLEU/ROUGE · benchmarks · human · LLM-judge.
Interview Q&A
Why is accuracy a bad metric for rare-event detection (e.g. fraud)?

With heavy class imbalance, a model can hit 99% accuracy by always predicting "not fraud" while catching zero actual fraud. Accuracy hides this. Precision, recall, and F1 (or PR-AUC) reveal whether the rare positive class is actually being detected.

When do you optimize for recall over precision?

When missing a positive is costlier than a false alarm — e.g. cancer screening or fraud detection, where you'd rather flag some false positives than let a real case slip through. Optimize for precision when false alarms are expensive or annoying, like a spam filter blocking real email.

What is perplexity, intuitively?

It measures how "surprised" the model is by real text — roughly, the average number of equally-likely choices it's deciding among at each token. Lower perplexity means the model predicts the next token more confidently and accurately. It evaluates language modelling quality, not task correctness.

ADV-01 · making models helpful & safe

RLHF & Alignment

Advanced
Theory

A pre-trained LLM predicts text but isn't naturally helpful, honest, or safe. Alignment is the process of getting a model to behave the way humans want. The dominant technique has been RLHF — Reinforcement Learning from Human Feedback.

RLHF works in stages: collect human preferences (people rank or compare model outputs), train a reward model to predict those preferences, then use reinforcement learning (e.g. PPO) to update the LLM so it produces outputs the reward model scores highly. Newer methods like DPO (Direct Preference Optimization) skip the separate reward model and optimize on preference pairs directly. The goal is a model that's helpful, harmless, and honest.

Cheat sheet
quick recall
AlignmentGetting model behaviour to match human intent/values.
RLHF stepsCollect preferences → train reward model → RL-tune the LLM.
Reward modelLearns to score outputs the way humans would rank them.
DPOOptimizes preference pairs directly, no separate reward model.
GoalHelpful · harmless · honest assistant behaviour.
Interview Q&A
Why isn't a pre-trained model directly useful as an assistant?

Because it only learned to continue text, not to follow instructions or be helpful. Ask it a question and it might respond with more questions or unsafe content, simply because that's a probable continuation. Instruction-tuning and RLHF reshape it to respond as a cooperative, safe assistant.

What is reward hacking in RLHF?

When the model learns to maximize the reward-model score without genuinely satisfying the human intent — e.g. becoming verbose, sycophantic, or confidently formatted because the reward model over-rewards those traits. It's a case of optimizing the proxy (reward model) instead of the true goal, which is why reward models and evaluation need care.

ADV-02 · doing more with less compute

PEFT, LoRA & Quantization

Advanced
Theory

Full fine-tuning of a large model means updating all its parameters — huge memory and cost. PEFT (Parameter-Efficient Fine-Tuning) updates only a tiny fraction instead. LoRA is the popular method: it freezes the original weights and trains small low-rank "adapter" matrices, so you tune millions of parameters instead of billions, and can swap adapters per task.

Quantization attacks the other cost — running the model. It stores weights in lower precision (e.g. 16-bit → 8-bit or 4-bit integers), shrinking memory and speeding inference, usually with minor accuracy loss. Together, LoRA + quantization (e.g. "QLoRA") let people fine-tune and serve large models on modest hardware.

Cheat sheet
quick recall
PEFTFine-tune a small subset of params, not all of them.
LoRAFreeze base weights; train small low-rank adapters. Swappable.
QuantizationLower-precision weights (8/4-bit) → less memory, faster, minor loss.
QLoRAQuantized base + LoRA → fine-tune big models on small GPUs.
Why careCost, memory, and deployability — not just accuracy.
Interview Q&A
How does LoRA cut fine-tuning cost so dramatically?

It freezes the original weights and injects small low-rank matrices whose product approximates the needed weight update. You only train those tiny matrices — often well under 1% of the parameters — so memory and compute drop sharply, and the adapters are small files you can store and swap per task.

What's the tradeoff with quantization?

Lower precision means less memory and faster inference, but some accuracy/quality loss from rounding. Modern techniques (8-bit, careful 4-bit) keep the loss small for most tasks, but very aggressive quantization can degrade quality, so you validate on your actual workload.

ADV-03 · models that act

AI Agents & Tool Use

Advanced
Theory

An agent uses an LLM as a reasoning engine inside a loop to accomplish goals that take multiple steps. Rather than answering once, it can plan, choose to call a tool (web search, code execution, a database, an API), observe the result, and decide what to do next — repeating until done. This is often described as a reason-and-act cycle.

Tool use / function calling is the mechanism: the model emits a structured request to call a function, the system runs it, and feeds the result back into the context. Agents add memory (to persist state), planning (to break down tasks), and sometimes multiple cooperating agents. The hard parts are reliability, knowing when to stop, and recovering from errors that compound across steps.

Diagram
Cheat sheet
quick recall
Agent loopPlan → act (tool) → observe → repeat → finish.

AddsMemory, planning, tools, sometimes multi-agent collaboration.
vs ChatbotChatbot answers once; agent takes actions toward a goal.
Hard partsReliability, error compounding, stopping conditions, cost.
Interview Q&A
How does function calling actually work under the hood?

You describe available tools (name, purpose, parameters) to the model. When it decides a tool is needed, it outputs a structured call (e.g. JSON with the function name and arguments) instead of a normal answer. Your application executes that function, then feeds the result back into the context so the model can continue reasoning with it.

Why are agents harder to make reliable than single LLM calls?

Because errors compound over steps — a wrong decision early derails everything after it. Agents also depend on external tools that can fail, must decide when to act and when they're finished, and can loop or run up cost. Mitigations: guardrails, step limits, validation of tool outputs, retries, and human-in-the-loop for risky actions.

What's the difference between RAG and an agent that searches?

Basic RAG is a fixed one-shot retrieve-then-answer pipeline. An agent decides dynamically whether to search, can search multiple times, refine its queries based on what it finds, and combine tools. RAG is a step; an agent can orchestrate retrieval as one of many actions in a loop.

ADV-04 · the connector standard

Model Context Protocol (MCP)

Advanced
Theory

MCP (Model Context Protocol) is an open standard for connecting AI applications to external tools and data sources in a uniform way. The problem it solves: before a standard, every integration between an AI app and a service (Slack, a database, GitHub) was custom-built — an N×M explosion of one-off connectors.

MCP defines a common client–server interface so any compliant AI app (the client/host) can talk to any compliant MCP server that exposes tools, resources, or prompts. The common analogy is "a USB-C port for AI": one standard plug instead of a different cable for every device. It makes agent tool ecosystems interoperable and reusable.

Cheat sheet

RolesHost/client (the AI app) ↔ MCP server (exposes tools/data).
ExposesTools (actions), resources (data), prompts.

Interview Q&A
What problem does MCP solve?

The integration explosion. Without a standard, connecting M AI applications to N tools needs up to M×N bespoke integrations. MCP provides one common protocol so any client and any server speak the same language — write a tool server once and any MCP-compatible app can use it, and vice versa.

How does MCP relate to function calling?

Function calling is the model-level ability to request a tool. MCP is the standardized transport and interface for where those tools live and how the app discovers and invokes them. MCP can supply the catalog of tools that the model then calls — they operate at different layers and complement each other.

ADV-05 · beyond text

Multimodal Models

Advanced
Theory

Multimodal models handle more than one type of data — text, images, audio, video — often together. A vision-language model can look at an image and answer questions about it; others generate images from text or transcribe speech.

The common trick is to project each modality into a shared representation space (shared embeddings), so the model can reason across them. Images, for instance, get encoded into tokens/embeddings that sit alongside text tokens in the same Transformer. This is what enables "describe this photo," "read this chart," or "generate an image of…" in a single system.

Cheat sheet
quick recall
MultimodalWorks across text, image, audio, video.
Key ideaMap every modality into a shared embedding space.
Vision-languageEncode image → tokens beside text → reason jointly.
ExamplesImage Q&A, chart reading, text-to-image, speech-to-text.
EnablesOne model, many input/output types.
Interview Q&A
How does a model "see" an image if Transformers process tokens?

An image encoder turns the image into a sequence of embeddings (e.g. by splitting it into patches and encoding each). Those embeddings are projected into the same space as text tokens and fed into the Transformer alongside the words, so the model attends over image and text jointly.

What does "shared embedding space" buy you?

It lets the model relate different modalities by meaning — the embedding of the word "dog" and the embedding of a dog photo land near each other. That alignment is what enables cross-modal tasks like captioning, retrieval ("find images matching this text"), and answering questions about an image.

ADV-06 · scaling smartly

Mixture of Experts (MoE)

Advanced
Theory

Mixture of Experts is an architecture that grows a model's total parameters without proportionally growing its per-token compute. Instead of one big dense network, it has many "expert" sub-networks plus a router (gating network) that, for each token, activates only a small subset of experts.

So a model might have, say, hundreds of billions of total parameters but only activate a fraction per token. You get the capacity of a huge model at the inference cost of a much smaller one. The tradeoffs are higher memory (all experts must be stored) and engineering complexity around balanced routing.

Cheat sheet
quick recall
MoEMany expert sub-nets; a router picks a few per token.
SparseTotal params huge, active params per token small.
WinBig-model capacity at smaller-model compute cost.
CostHigh memory (store all experts) + routing complexity.
Term"Active parameters" ≠ "total parameters."
Interview Q&A
Why does MoE separate "total" from "active" parameters?

Because only a subset of experts fires per token. Total parameters set the model's overall capacity/memory, while active parameters determine the compute per token. MoE decouples these so you can scale capacity cheaply — more knowledge without proportionally more flops at inference.

What's a key challenge in training MoE models?

Load balancing the router. If the gating network sends most tokens to a few favourite experts, the others go undertrained and capacity is wasted. Training uses auxiliary balancing losses to spread tokens across experts. Memory and distributed-systems complexity are the other big challenges.

ADV-07 · serving fast & cheap

Inference Optimization

Advanced
Theory

Because inference happens constantly, making it fast and cheap is a core production concern. Key levers: the KV cache stores the keys/values of past tokens so the model doesn't recompute them each step (essential for generation speed). Batching serves many requests together to maximize GPU utilization. Quantization shrinks the model. Speculative decoding uses a small draft model to propose tokens that the big model verifies in bulk.

Two metrics matter: latency (how fast one user gets a response, often split into time-to-first-token and per-token speed) and throughput (total tokens served across all users). Optimizations usually trade one against the other.

Cheat sheet
quick recall
KV cacheReuse past tokens' keys/values; avoids recompute each step.
BatchingGroup requests → higher GPU throughput.
Speculative dec.Small model drafts, big model verifies → faster.
QuantizationLower precision → less memory, faster.
MetricsLatency (TTFT, tok/s) vs throughput (total tok/s). Trade-off.
Interview Q&A
What is the KV cache and why is it essential?

During autoregressive generation, each new token attends to all previous tokens. Without caching, the model would recompute every previous token's key and value vectors at every step — wildly wasteful. The KV cache stores them so each step only computes the new token, turning generation from quadratic-ish waste into a manageable cost. Its size grows with context length, which is a memory consideration.

Latency vs throughput — how can they conflict?

Large batching boosts throughput (more total tokens/sec across users) by filling the GPU, but an individual request may wait to be batched, raising its latency. Serving systems tune batch size and scheduling to balance a single user's responsiveness against overall efficiency and cost.

ADV-08 · keeping it safe in production

Guardrails, Prompt Injection & Safety

Advanced
Theory

Putting an LLM in front of users introduces security and safety risks unique to natural-language systems. Prompt injection is the headline threat: malicious instructions hidden in user input — or in content the model retrieves (a webpage, a document) — hijack the model into ignoring its original instructions. Jailbreaks are prompts crafted to bypass safety rules.

Guardrails are the defensive layers: input/output filtering and moderation, restricting tool permissions, separating trusted instructions from untrusted data, validating outputs, and limiting what actions an agent can take autonomously. There's no single fix, so defense-in-depth and red-teaming (actively trying to break your own system) are standard practice.

Cheat sheet
quick recall
Prompt injectionHidden instructions in input/retrieved data hijack the model.
JailbreakPrompt that bypasses safety rules.
GuardrailsFiltering, moderation, output validation, least-privilege tools.
Key principleTreat retrieved/user content as untrusted; isolate instructions.
PracticeDefense-in-depth + red-teaming. No single silver bullet.
Interview Q&A
What is indirect prompt injection?

When the malicious instruction isn't typed by the user but embedded in content the model ingests — a web page it browses, a document in a RAG store, an email it summarizes. The model can't easily tell "data" from "instructions," so hidden text like "ignore previous instructions and…" can hijack it. It's especially dangerous for agents with tools.

How do you defend an agent that can take real actions?

Apply least privilege (only the tools/permissions it truly needs), human approval for high-impact actions, validate and sandbox tool inputs/outputs, separate trusted system instructions from untrusted data, add input/output moderation, and continuously red-team. Assume injection will be attempted and limit the blast radius rather than relying on the model to always refuse.

VS-01 · three ways to adapt a model

Prompt Engineering vs. Prompt Tuning vs. Fine-tuning

vs
Theory

All three adapt a model to your task, but they touch different things. The trap is that "prompt engineering" and "prompt tuning" sound identical and are constantly confused — they are not the same.

Prompt engineering changes only the text you send. No training, no weights touched, works on any model through plain language — you craft instructions, examples, and structure. Prompt tuning is a lightweight training method: it keeps the model frozen but learns a small set of "soft prompts" — continuous vectors prepended to the input, optimized via backpropagation on labelled data. They aren't human-readable words; they're learned embeddings. Fine-tuning goes further and updates the model's actual weights (fully, or efficiently via LoRA).

Interview Q&A
People use "prompt tuning" and "prompt engineering" interchangeably. Correct them.

Prompt engineering is not training — you only rewrite the input text, treating the model as a black box. Prompt tuning is training: the model stays frozen, but you learn small continuous soft-prompt vectors via backpropagation on labelled examples. One is manual wording; the other is a parameter-efficient fine-tuning technique that produces non-human-readable learned prompts.

Where does prompt tuning sit relative to LoRA?

Both are parameter-efficient fine-tuning (PEFT) methods that freeze the base model. Prompt tuning learns extra input vectors (soft prompts) and changes nothing inside the network; LoRA learns small low-rank updates to the model's internal weight matrices. LoRA generally adapts behaviour more deeply; prompt tuning is even lighter.

Cheapest to most expensive — order them and say why.

Prompt engineering → prompt tuning → fine-tuning. Prompt engineering needs no training or data. Prompt tuning trains only a tiny set of soft-prompt parameters on labelled data. Full fine-tuning updates all (or, with LoRA, a meaningful subset of) weights and needs the most data, compute, and expertise.

VS-02 · the grounding question

LLM vs. RAG vs. Fine-tuning

vs
Theory

"LLM vs RAG" is a slightly unfair comparison — and saying so is the smart answer. An LLM is the model; RAG is a technique you wrap around an LLM. A plain LLM answers purely from what it memorized during training (limited by its knowledge cutoff). RAG adds a retrieval step that fetches relevant external documents and feeds them into the prompt, so the LLM answers from current, specific, sourced knowledge.

The real decision is usually RAG vs fine-tuning: do you need new knowledge or new behaviour? RAG injects facts at query time (easy to update, supports citations, no retraining). Fine-tuning changes how the model responds (style, format, task) by altering weights. They're complementary — many systems use a fine-tuned model with RAG.

Interview Q&A
"What's the difference between an LLM and RAG?"

They're not alternatives at the same level. The LLM is the model that generates text from its trained parameters. RAG is an architecture around the LLM that retrieves relevant external documents and adds them to the prompt before generation. So RAG uses an LLM to produce answers grounded in fetched, up-to-date, sourceable information rather than memory alone.

RAG or fine-tuning for a customer-support bot over your product docs?

Lead with RAG: product docs change often, you want answers grounded in the exact current docs, and you want citations — all of which RAG handles by updating the knowledge base, no retraining. Add fine-tuning only if you also need a consistent tone/format the prompt can't reliably enforce. In practice: RAG for the knowledge, optional light fine-tune for the voice.

Can RAG and fine-tuning be combined?

Yes, and often they should. Fine-tune the model for how to behave (domain style, output structure, refusal patterns) and use RAG for what facts to ground in. They address different problems — behaviour vs knowledge — so they stack cleanly.

VS-03 · the ML fundamentals deep-dive

Supervised vs. Unsupervised — Algorithms & Problem Types

vs
Theory

The dividing line is one thing: are there labels (known target answers) in the training data?

Supervised learning has labelled data and learns to map inputs to those known outputs. It solves two problem types: classification (predict a category — spam/not-spam, disease/no-disease) and regression (predict a continuous number — house price, delivery time). Unsupervised learning has no labels; it finds hidden structure. Its main problem types are clustering (group similar points) and dimensionality reduction / association (compress features, find co-occurrence). Beyond these sit semi-supervised (a little labelled + lots of unlabelled) and reinforcement learning (learn from rewards).

Interview Q&A
What are the problem types under each, with one example?

Supervised → classification (is this email spam?) and regression (what will this house sell for?). Unsupervised → clustering (segment customers into natural groups) and dimensionality reduction / association (compress 100 features to 10; "people who buy X also buy Y").

You have data but no labels. What can you actually do?

Use unsupervised methods: cluster to discover segments (K-Means, DBSCAN), reduce dimensions to explore or visualize (PCA, UMAP), or mine associations. If labelling a small subset is feasible, semi-supervised learning lets a little labelled data guide the rest — common when labels are expensive.

How do you choose between logistic regression and a random forest?

Start simple. Logistic regression is fast, interpretable, and strong when the relationship is roughly linear and you want explainability. Random forest / gradient boosting capture non-linear interactions and usually win on messy tabular data, at the cost of interpretability and tuning. Cross-validate both and let the validation metric — chosen for your error costs — decide.

VS-04 · the classic trap question

KNN vs. K-Means

vs
Theory

They sound alike and both use "k" and distances, so interviewers love this one. They are completely different. KNN (k-nearest neighbours) is supervised: given labelled points, it classifies a new point by the majority label of its k closest neighbours. K-Means is unsupervised: given unlabelled points, it groups them into k clusters by iteratively moving cluster centroids.

The "k" means different things too: in KNN it's how many neighbours vote; in K-Means it's how many clusters to form. KNN is a "lazy" learner (no real training step — it just stores data); K-Means actually fits centroids during training.

KNN is supervised classification using labelled neighbours; K-Means is unsupervised clustering of unlabelled data — same "distance" intuition, opposite problems.

Why is KNN called a "lazy learner"?

Because it does no real work at training time — it just memorizes the dataset. All computation is deferred to prediction, when it measures distances to find the nearest neighbours. K-Means, by contrast, is "eager": it computes cluster centroids during training.

VS-05 · model families

Encoder vs. Decoder · GPT vs. Diffusion

vs
Theory

Two model-family comparisons come up a lot. First, encoder vs decoder Transformers. Encoder-only models (e.g. BERT) read the whole input bidirectionally and are built for understanding tasks — classification, embeddings, search. Decoder-only models (e.g. GPT) generate text left-to-right and are built for producing text. (Encoder-decoder models like T5 do both, e.g. translation.)

Second, GPT-style vs diffusion. GPT-style models are autoregressive — they generate tokens one at a time, great for text. Diffusion models generate by starting from noise and iteratively denoising toward a result — the dominant approach for high-quality image and video generation.

Interview Q&A
When would you pick an encoder-only model like BERT over GPT?

For understanding tasks, not generation: text classification, named-entity recognition, semantic search, or producing embeddings. Encoder models read the whole sequence bidirectionally, which suits comprehension. Use a decoder (GPT-style) when the job is to generate fluent text.

Why are images usually made with diffusion, not autoregressive models?

Generating an image pixel-by-pixel autoregressively is slow and struggles with global coherence. Diffusion starts from noise and refines the whole image over many denoising steps, which produces high-quality, globally consistent results — and conditions naturally on a text prompt.

Interview Q&A
What's the single most common LLM-engineering interview topic right now?

RAG. Most production LLM apps use it, so expect to design a pipeline, justify chunking and retrieval choices (sparse vs dense, hybrid search), discuss productionizing it (scale, retrieval errors), and explain how you'd detect and reduce hallucinations within it.

How do GenAI system-design interviews differ from classic system design?

You still scope requirements and components, but add LLM-specific concerns: how to integrate the model, structure prompts, manage the token/cost budget, choose RAG and a vector DB, ground outputs to avoid unsafe answers, and evaluate quality (often with an A/B framework or a feedback loop). Asking clarifying questions — data freshness, privacy, on-prem vs API — is part of the score.

JOB-02 · scenarios & whiteboard

Practical & Scenario Questions

Practical
How to approach these

Scenario questions reward structured reasoning, not a memorized answer. Clarify the requirement, name the likely culprits or options, pick one with a trade-off justification, and say how you'd measure success. The Q&A below models that shape.

Interview Q&A
Your RAG app returns irrelevant or wrong answers. How do you debug it?

Isolate retrieval vs generation first. Inspect what chunks were actually retrieved: if they're wrong, the problem is upstream — bad chunking (too big/small), weak embedding model, too-small top-k, or no relevant doc in the store. Fixes: better chunking with overlap, a stronger embedding model, hybrid (keyword + vector) search, and re-ranking. If the right context was retrieved but the answer is still wrong, look at the prompt, context ordering, and the model. Add evals so you can measure each fix.

Your LLM feature is too expensive. How do you cut cost ~50%?

Attack tokens and model choice. Shorten prompts (trim few-shot examples, compress the system prompt), cap output length, and cache repeated calls. Route easy queries to a smaller/cheaper model and reserve the big model for hard ones. For self-hosted: quantize and batch requests. Retrieve fewer, better chunks so context is smaller. Measure cost per request before and after.

Production latency is too high. What do you do?

Stream the response so time-to-first-token feels fast. Use a smaller or distilled model where quality allows, enable the KV cache and request batching, and consider speculative decoding. Shrink the prompt and retrieved context (long context = slower). Cache frequent answers. Distinguish the two metrics: time-to-first-token vs total generation time, and optimize the one users feel.

The model gives different answers each time. Is that a bug, and how do you fix it?

Usually expected: generation is stochastic. For reproducible, factual outputs, set temperature near 0 (and fix the seed if the API supports it) so it picks the most probable tokens. For tasks needing variety (brainstorming), keep it higher. If you need consistency and structure, also constrain the output format (e.g. a JSON schema / structured outputs).

Design a chatbot that answers questions over our internal company documents.

This is a RAG system. Offline: ingest docs → clean → chunk (with overlap) → embed → store in a vector DB. Online: embed the user's question → retrieve top-k (ideally hybrid search + re-ranking) → assemble a prompt with the chunks and instructions → generate a grounded answer with citations. Add guardrails (refuse when nothing relevant is retrieved), access control on private docs, an eval set, and logging/feedback to improve retrieval. Mention re-embedding cadence as docs change.

How would you evaluate an LLM feature before launching?

Don't rely on vibes. Build a representative eval set with expected behaviours, score with a mix of automated metrics, an LLM-as-judge, and human review for high-stakes cases. Track task success, hallucination rate, latency, and cost. Run A/B tests on prompts and retrieval in production, and collect thumbs up/down to feed continuous improvement.

A user tries to make your bot ignore its instructions. How do you defend it?

That's prompt injection. Treat all user and retrieved content as untrusted, keep trusted system instructions separated, and add input/output moderation. Give any tools least privilege and require approval for high-impact actions. Validate and sandbox tool calls, constrain outputs, and red-team continuously. Assume some attempts succeed and limit the blast radius rather than trusting the model to always refuse.
